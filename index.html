02 / how I work

From product brief to a healthy release

How I take a feature from idea to production and keep it working afterwards. I follow the same six steps whether it's a one-screen fix or a new hardware integration.

  1. 01

    Shape

    Work through the brief with product and design, split it into slices that can ship on their own, and agree the API contracts and analytics events before any code.

    → scoped tickets, API contract
  2. 02

    Design

    Anything that touches native code, persisted state or the release process gets a short design note covering state shape, failure modes, and how to roll it out and back.

    → design note, reviewed
  3. 03

    Build

    Code is grouped by feature, with logic in hooks rather than screens. I only write Swift or Kotlin where JavaScript can't reach, and wrap shared behaviour like location or BLE once instead of in every screen.

    → typed, reviewed PRs
  4. 04

    Verify

    Jest tests for the logic, with native modules mocked. Detox for the critical flows. Then hands-on passes on low-end Android phones and iOS, because that's where field users are.

    → green tests, device sign-off
  5. 05

    Ship

    JavaScript-only fixes go out over the air the same day. Native changes go through the App Store and Play Console. A pre-deploy check blocks bad bundles, and rollback is one command.

    → release, rollback ready
  6. 06

    Observe

    Sentry and Crashlytics with source maps, and new crashes triaged the same day. An in-app developer mode helps debug issues in the field. Whatever we learn goes back into step 01.

    → 99.51% crash-free

03 / engineering notes

Problems worth writing down

Three production problems, how I diagnosed them, and what I built to fix them.

location · Android Detecting a GPS that has silently hung +

Problem

On some phones the GPS stops working until the phone is restarted. Location is on, permission is granted and the provider is enabled, yet every request times out or returns a coarse Wi-Fi fix. No setting shows anything wrong, so runners carried on while their tracking went stale.

Approach

  • Wrapped getCurrentPosition once at module load, so every existing call site is monitored without being edited.
  • After several failures in a row while the app is open, rule out settings causes first: location off, provider off, permission, precise location.
  • Then request a fresh fix from Google's fused provider and the raw LocationManager at the same time. If neither returns a usable fix, the GPS is stuck.
  • Ask the runner to restart the phone, re-check on resume and on a timer, and close the prompt as soon as a fix arrives.

Result

A failure nobody could see is now detected from how the GPS behaves and fixed on the spot. The logic is covered by Jest tests that mock app state, location settings and the native modules.

release · OTA An OTA deploy that refuses to ship blind +

Problem

With self-hosted OTA (Hot Updater on Firebase), each update fully replaces the JavaScript bundle inside the installed app. If Sentry is missing from a bundle, for example commented out while debugging and never restored, everyone who installs that update runs without crash reporting. Play Console then shows only a bare JavascriptException, and this can go unnoticed for weeks.

Approach

$ yarn ota
✓ verify-sentry  source ok
✓ hot-updater    bundle built (Hermes)
✓ hot-updater    uploaded → production
✓ verify-sentry  bundle ok
# if anything slips through:
$ yarn ota:rollback

A check runs before the deploy. It strips comments from the source, so a commented-out Sentry.init doesn't pass, and blocks the release if Sentry is missing. A second check inspects the built bundle afterwards. Updates are matched to the app version, so a bundle never reaches a binary it isn't compatible with.

Result

Same-day hotfixes and about 70% faster releases, without risking a release with no crash reporting. Bad releases are reversed with one command.

networking · config Moving 8 backend services without an app release +

Problem

API hosts were hard-coded in the app, so every backend migration meant shipping a new store build and waiting for runners to update.

Approach

  • Each app launch reads the base URLs from Firebase Remote Config: one root host that expands to all 8 services, plus an optional override for any single service.
  • Every value is validated. If the fetch fails, times out or returns something invalid, the app uses the last values that worked, then the local defaults.
  • Keys are prefixed per app, because Remote Config shares one namespace across the Firebase project.

Result

The backend team can move or split services without a mobile release, and a bad config value can't take the app offline.
